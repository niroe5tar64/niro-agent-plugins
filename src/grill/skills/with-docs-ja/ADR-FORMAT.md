# ADR の書式

ADR は `docs/adr/` に置き、連番で命名する: `0001-slug.md`, `0002-slug.md` 等。

`docs/adr/` ディレクトリは遅延作成する — 最初の ADR が必要になった時点で作る。

## テンプレート

```md
# {決定事項の短いタイトル}

{1〜3 文: 文脈は何か、何を決めたか、なぜか}
```

これだけでよい。ADR は 1 段落で十分。価値は、決定が「なされた」事実とその「理由」を記録することにあり、セクションを埋めることにはない。

## オプションセクション

本当に価値があるときだけ含める。多くの ADR では不要。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`） — 決定が見直される可能性があるとき
- **Considered Options** — 却下した代替案を覚えておく価値があるときだけ
- **Consequences** — 自明でない波及効果を明示する必要があるときだけ

## 採番

`docs/adr/` をスキャンし、最大番号に +1 する。

## ADR を提案するタイミング

以下 3 つが全て満たされる必要がある:

1. **取り消しが難しい** — 後で考えを変えるコストが意味のある大きさ
2. **文脈なしでは驚かれる** — 将来の読み手がコードを見て「なぜわざわざこのやり方？」と思う
3. **本物のトレードオフの結果** — 真に複数の選択肢があり、特定の理由で 1 つを選んだ

決定が簡単に取り消せるならスキップする — どうせ取り消す。驚かれないなら、誰も理由を気にしない。本当の代替案が無かったなら、「自明なことをやった」以上に記録すべきものは無い。

### 対象になるもの

- **アーキテクチャの形状。** 「モノレポを採用」「書込モデルはイベントソーシング、読込モデルは Postgres に投影」
- **コンテキスト間の統合パターン。** 「Ordering と Billing は同期 HTTP ではなく domain event で連携する」
- **ロックインを伴う技術選定。** データベース、メッセージバス、認証プロバイダ、デプロイ先。あらゆるライブラリではなく、差し替えに四半期かかる類のもの。
- **境界とスコープの決定。** 「Customer データは Customer コンテキストが所有し、他コンテキストは ID 参照のみ」。明示的な「やらない」は「やる」と同じくらい価値がある。
- **自明な道筋からの意図的な逸脱。** 「ORM ではなく手書き SQL を使う、理由は X」。普通の読み手なら逆を仮定する類のもの。次のエンジニアが「直す」のを防ぐ。
- **コードからは見えない制約。** 「コンプライアンス要件で AWS は使えない」「パートナー API 契約で応答時間は 200ms 未満」
- **却下した代替案、却下理由が非自明なとき。** GraphQL を検討して REST を選んだ理由が微妙なら記録する — さもないと半年後にまた GraphQL を提案される。
