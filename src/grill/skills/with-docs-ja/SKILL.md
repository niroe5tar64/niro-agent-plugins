## ドメイン文脈の構成

多くのリポジトリは単一コンテキスト:

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

ルートに `CONTEXT-MAP.md` がある場合は複数コンテキスト。マップが各コンテキストの所在を示す:

```
/
├── CONTEXT-MAP.md
├── docs/adr/                         ← システム全体の決定
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← コンテキスト固有の決定
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

ファイルは遅延作成する。`CONTEXT.md` が無ければ最初の用語が固まった時点で作る。`docs/adr/` が無ければ最初の ADR が必要になった時点で作る。

## セッション中の振る舞い

### 辞書と突き合わせる

ユーザーが使った語が `CONTEXT.md` の語彙と衝突したら即座に指摘する。「辞書では『キャンセル』は X と定義されていますが、今は Y を指していますか？どちらですか？」

### 曖昧な語に正準名を提案する

「アカウント」のような多義語が出たら、正準名候補を提示する。「Customer（注文する人）と User（ログインする人）のどちらですか？」

### 具体シナリオで境界を詰める

ドメイン関係が議論になったら、エッジケースを突くシナリオを 1 つ作って境界条件を言語化させる。

### コードと突き合わせる

「こう動くはず」と言われたら、Read / Grep で確認する。矛盾があれば surface する。

### CONTEXT.md をインラインで更新する

用語が確定したら、その場で `CONTEXT.md` に書く。バッチで溜めない。書式は [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) に従う。

`CONTEXT.md` は用語辞書専用。実装詳細・スペック・スクラッチパッドとして使わない。

### ADR は控えめに提案する

以下 3 条件全てを満たすときだけ ADR を提案する:

1. **取り消しが難しい** — 後で変えるコストが大きい
2. **文脈なしでは驚かれる** — 半年後の読み手が「なぜこのやり方？」と思う
3. **本物のトレードオフ結果** — 真に複数の選択肢があり、明確な理由で選んだ

1 つでも欠けたらスキップする。書式は [ADR-FORMAT.md](./ADR-FORMAT.md) に従う。
